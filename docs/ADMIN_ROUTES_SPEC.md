# ТЗ для Sol-админка: структура страниц, навигация и ЧПУ

Дата: 2026-11-03.
Основа аудита: `main` на коммите `3bc0ffadbaab10a441ec6009b34d4959b8276941`. Перед реализацией проверить изменения актуального main и рабочие контракты другого агента.

## 1. Границы задачи

Перестроить интерфейсный слой админки: маршруты, навигацию, шаблоны, адреса карточек, поиск/фильтры/пагинацию и совместимость старых ссылок. Сохранить действующую бизнес-логику.

Голосовым сервисом занимается другой агент. Не менять виджет, приём/хранение аудио, транскрипцию, промпты разбора, формат результата, воркеры, очереди обработки, алгоритмы модерации, атомарное применение пакета, автоодобрение, полномочия Алекса и его персональный вход. Не редактировать `docs/VOICE_SERVICE_SPEC.md`. Общие маршруты карточек отзывов — часть интерфейсного контракта, их можно реализовать поверх существующих сервисов.

Не возвращать черновики страниц: в актуальном main сохранение уже непосредственно обновляет сайт и сохраняет историю. Не менять модель версий и правила восстановления. Сохранить независимое редактирование вступления, восстановление звезды и инициализацию controls после HTMX swaps из последних коммитов main.

Допустимы небольшие миграции публичных номеров/slug/алиасов, необходимые для адресов. Первичные UUID, внешние ключи, аудио, отзывы, логи и исторические данные сохраняются. Не переписывать доменную модель ради URL.

## 2. Правила адресов

- Раздел и конкретная запись определяются путём; поиск, фильтры и пагинация — query-параметрами.
- Новые пользовательские ссылки не содержат UUID, `tab=`, `message=`, выбора записи через `review=`, `job=` или `location=<uuid>`.
- Использовать настраиваемый BASE_PATH; текущий — `/guide`. Не зашивать домен или корневой путь в шаблоны/JS.
- Адреса админки без завершающего слеша; нормализовать альтернативный вариант. Существующий `/guide` → `/guide/` с 302 сохранить.
- У сущности один канонический адрес независимо от места перехода. При переименовании старый адрес ведёт на новый.
- GET читает данные. Сохранение, восстановление и запуск существующих операций остаются POST с текущими проверками прав и CSRF.

## 4. Размещение существующих возможностей

### Локация

Карточка содержит настройки локации, ссылку на публичную страницу, редактор, историю и кнопку наполнения. Выбор модели для запуска и переход к соответствующему логу находятся здесь же. Глобальный промпт/модель наполнения — в настройках. Сам алгоритм наполнения и его результат не меняются.

Редактор страницы и редактор данных локации различаются адресами, но используют текущие application-сервисы. Перенос форм не должен потерять независимое сохранение вступления, поля, validation errors и проверки ожидаемой версии. Самостоятельный ресторанный экран использует имеющиеся правила сохранения и привязки к локации; не вводить новый способ публикации.

### Отзывы

Очередь находится только в `/admin/reviews`. Карточка отзыва показывает текст, аудио, доступные результаты обработки и относящиеся к нему предложения. Предложения не получают собственной навигационной сущности. При необходимости выделить элемент на странице использовать якорь, например `#change-2`.

Модель принятия пакета реализуется другим агентом. Этот PR переносит экран и ссылки; не разрабатывает новый протокол одобрения или частичное одобрение. Существующие действия подключать к текущим сервисам; если другой агент уже предоставил новый контракт, использовать его без изменения семантики. Из карточки отзыва открываются существующие общие логи `/logs/{slug}/{number}`.

### Логи

Страница одна: `/logs/...`. Выбранный лог слева, сайдбар запросов/поиска/фильтров справа на широком экране. Один вертикальный скролл документа, без вложенных областей прокрутки списка и JSON. На узком экране последовательная компоновка с доступным переходом к списку. Сохранить выделение выбранного запроса и читаемость длинных ответов.

На той же странице авторизованный видит доступные ему кнопки. Проверки прав на backend сохраняются, как и текущие ограничения видимости голосовых данных/аудио. Не менять правила публичного доступа к логам. Существующие status/JSON/audio endpoints и клиентский polling продолжают работать. Удалить пустые query-параметры из ссылок.

### Настройки и история

Перенести существующие настройки по согласованным адресам. Настройки голоса, отсутствующие в текущем backend, не реализовывать заново: их контракт принадлежит другому агенту. В навигации подключать готовые экраны; до появления capability показать честное состояние «недоступно в этой версии», а не фиктивную работающую форму.

Историю показывать из имеющихся данных. Не придумывать автора/дифф для старых событий, где они не были сохранены. Не менять схему бизнес-аудита в этом PR. Исторический снимок страницы должен показывать сохранённое содержимое, а не сегодняшние поля ресторана.

## 5. Читаемые идентификаторы

Локация: существующий slug (`ivanovo`). Исторические aliases/redirects сохраняются.

Ресторан: slug названия + постоянный глобальный номер (`ogonek-27`). Номер назначается один раз, не зависит от сортировки и количества строк. Филиалы с самостоятельными карточками получают разные номера. Ресторан может входить в несколько локаций, поэтому канонический адрес не привязывать к одной подборке. При переименовании прежняя читаемая часть перенаправляет на актуальную.

Отзыв: исходная локация приёма + постоянный номер внутри неё (`ivanovo/12`). Если другой агент уже ввёл такой идентификатор, переиспользовать его, не добавлять конкурирующую нумерацию. Назначение новых номеров — атомарное, с ограничением уникальности. Смена связанного ресторана не меняет идентичность отзыва.

Версии и логи: сохранить существующие номера. Номер лога и номер версии страницы независимы; связывать ссылками, не приравнивать.

Backfill существующих идентификаторов должен быть детерминированным и безопасным при конкурирующем создании записей. Не переиспользовать выданные номера. Проверить reserved segments (`new` и другие), коллизии имён, неизвестный номер, смену slug и отсутствие redirect-циклов. Старые URL должны открывать ту же сущность после переименования.

## 6. Поиск, фильтры, пагинация

Допустимые примеры:

```text
/admin/locations?status=empty&q=иваново&page=2
/admin/restaurants?location=ivanovo&q=огонёк
/admin/reviews?location=ivanovo&status=pending&page=2
/admin/reviews?stage=failed
/admin/reviews?change=phone
/logs/ivanovo?status=failed
/admin/history?page=2
```

`status` у отзывов означает модерацию, `stage` — существующее техническое состояние. `change=phone` показывает отзывы с предложением телефона, не отдельную очередь предложений. Использовать реальные состояния и атрибуты, доступные через текущие сервисы; новые бизнес-статусы не вводить.

Не добавлять пустые параметры, значения по умолчанию и `page=1`. При изменении фильтра начинать с первой страницы. Неверные значения не должны давать 500. Ссылки карточек чистые, без наследования фильтров. Возврат к отфильтрованному списку и Back/Forward работают, несколько вкладок не перезаписывают друг другу фильтры через глобальное состояние сессии.

## 7. Обработчики, формы, HTMX

Разделить нынешний большой `admin(request)`/`tab` dispatcher на обработчики разделов и карточек. Разбить шаблоны по экранам, оставив общий layout/navigation. Использовать именованные маршруты/единый URL-helper. Presentation не должна выполнять SQL или заново реализовывать бизнес-правила.

При переносе POST можно вводить предметные адреса, например:

```text
POST /admin/locations/ivanovo/intro
POST /admin/locations/ivanovo/page
POST /admin/locations/ivanovo/generate
POST /admin/locations/ivanovo/versions/7/restore
```

Они вызывают прежние сервисы с прежними проверками и последствиями. Контракты POST обработки голоса/модерации согласовать с владеющим ими агентом, не переписывать самостоятельно. Не создавать отдельную кнопку публикации.

После успешного POST — 303 на канонический экран, уведомления через flash/HTML, не `message=` в URL. При ошибке сохранить введённые данные. Формы поддерживают обычный POST без JS; HTMX не ломает полный ответ, загрузку страницы напрямую, history и controls после swap. Сохранить защиту от кеширования приватных экранов и действующие auth/CSRF проверки.

## 8. Совместимость и переход

| Старый адрес | Новый |
| --- | --- |
| `/admin?tab=locations` | `/admin/locations` |
| `/admin?tab=locations&location=<uuid>` | `/admin/locations/{slug}` |
| `/admin?tab=locations&location=new` | `/admin/locations/new` |
| `/admin?tab=restaurants&location=<uuid>` | `/admin/restaurants?location={slug}` |
| `/admin?tab=reviews&review=<uuid>` | `/admin/reviews/{slug}/{number}` |
| `/admin?tab=fill` | `/admin/locations` |
| `/admin?tab=contacts` или `/admin/contacts` | `/admin/reviews?change=phone` |
| `/admin?tab=ratings` | `/admin/restaurants` с сохранением доступа к имеющимся оценкам |
| `/admin?tab=sessions` | `/admin/settings/sessions` |
| `/admin?tab=ai-audit&job=<uuid>` | существующий `/logs/{slug}/{number}` |

Старые GET перенаправляются после разрешения идентичности и проверки доступа, полезные поисковые фильтры сохраняются. Существующие отдельные адреса истории также перенаправляются на `versions`. `add=1` заменяется нормальной ссылкой/формой добавления, без потери функции при отключённом JS.

Не перенаправлять старые POST так, чтобы они выполнялись повторно. На переходный период допустимы адаптеры старых форм, вызывающие тот же текущий сервис. Старые публичные логи и персональная ссылка Алекса сохраняются. Весь новый UI генерирует только новые канонические ссылки.

Обновить `docs/LEGACY_REMOVAL.md`: перечислить прежние GET/POST adapters, `tab` dispatcher, URL-helper с message и условия удаления. Не удалять историю, внутренние UUID или применённые миграции.

## 9. Готовность и проверки

1. Все существующие функции админки доступны через новую структуру; прямые ссылки, обновление страницы, вход/возврат, Back/Forward и новая вкладка работают.
2. Новые навигационные URL без UUID/tab/message, фильтры используют slug и валидные значения. Пагинация сохраняет фильтры; первая страница без лишних параметров.
3. Миграция идентификаторов сохраняет записи/связи, номера уникальны при конкуренции, rename и legacy redirects ведут на ту же сущность.
4. Одна страница логов, сайдбар справа, один скролл, мобильная компоновка, кнопки по существующим правам; сохранены статус, JSON и аудио.
5. Сохранение локации/вступления/карточек и восстановление версии имеют прежние последствия: сразу актуальная страница и история. Нет нового этапа публикации.
6. Не потеряны формы/фильтры/отзывы/оценки/телефонные предложения/история/сессии; недоступные настройки не изображают реализованные возможности.
7. Регрессия HTMX, BASE_PATH, 302 `/guide` → `/guide/`, auth/CSRF и публичных страниц. Проверить новую навигацию браузерным тестом.
8. Diff не содержит изменений голосового pipeline, промптов разбора, worker, domain/application правил одобрения и автоодобрения. Читаемые идентификаторы — единственное допустимое пересечение persistence со смежной задачей; переиспользовать согласованный механизм.

Выполнить требуемые CONTRIBUTING проверки и релевантные тесты маршрутов/миграций/браузера. Платные AI-вызовы не нужны; production не трогать. PR описывает финальную таблицу адресов, миграции/совместимость, выполненные проверки и границы со смежной задачей. Реализация/деплой не выполняются самим сохранением этого ТЗ.
