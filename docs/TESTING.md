# Проверки приложения и релиза

## Путь CI

```text
последний успешный main CI → diff до проверяемого SHA → app / full
                                      ↓
                         кешируемый test Docker target
                                      ↓
                        линтеры и проверка типов
                                      ↓
              application + browser + [deployment для full]
                   максимум два процесса одновременно
                                      ↓
                 один production image → проверки → публикация
```

`deploy/ci_plan.py` выбирает дополнительные проверки по полному diff от последнего
успешного **push CI на main**, включая публикацию. Для PR проверяется merge commit.
Это сохраняет непроверенные инфраструктурные изменения в diff после неудачного CI:
последующая правка приложения не сможет незаметно пропустить проверку деплоя.
Удаления и обе стороны переименования учитываются. Если базовый SHA недоступен,
не является предком проверяемого SHA, история неизвестна или появились неизвестные
пути — профиль `full`. Ручной `workflow_dispatch` тоже всегда `full`.

| Проверка | app | full |
|---|---|---|
| Ruff, форматирование, mypy | Да | Да |
| Все unit и интеграционные проверки приложения | Да | Да |
| Все E2E браузерные сценарии | Да | Да |
| Контроллер установки/деплоя/отката | — | Да |
| Проверка установленного production-пакета, файлов, ASR и пользователя | Да | Да |
| Реальный запуск Guide/Voice, БД, HTTP-маршруты и ресурсы | Да | Да |
| Исторические cutover/backup/restore на настоящем PostgreSQL | — | Да |
| Nginx, ShellCheck, actionlint и Compose-конфигурация | — | Да |
| Проверки HTTPS/health/admin после настоящего деплоя и rollback | Да | Да |

`full` выбирается при изменениях Docker, lock/dependencies, workflow, `deploy/`,
миграций, конфигурации приложения, persistence, инфраструктуры интеграции Voice,
точек запуска/фоновых workers и самого механизма тестирования. Точный список —
в одном месте: `deploy/ci_plan.py`. Изменения бизнес-логики, HTML/CSS/JS, обычных
тестов приложения и документации получают `app`. Не добавляй обход проверки для
нового типа файла: неизвестные пути сначала требуют полного профиля.

## Параллельные группы

`deploy/run_tests.py` запускает до двух pytest-процессов в **одном** тестовом
контейнере. Дополнительных библиотек, контейнеров или сборок для этого нет.

- `application`: `tests/unit` и `tests/integration`, кроме `test_deployment.py`.
  Здесь есть и интеграционные проверки отдельных интерфейсов с Chromium.
- `browser`: `tests/e2e`.
- `deployment`: `tests/deployment` и `tests/integration/test_deployment.py`.

Каждый файл входит ровно в одну группу. Новый файл вне этих каталогов вызывает
ошибку назначения, а не молчаливый пропуск. Группы используют отдельные basetemp,
pytest cache, логи и JUnit XML. Ошибка любой выбранной группы блокирует публикацию.
У каждого теста БД по-прежнему отдельная случайная схема; порты серверов выделяются
динамически. PostgreSQL общий только как сервер, данные тестов не общие.

`var/test-results/` содержит логи, JUnit и `summary.json` с длительностями групп
и общим временем. CI сохраняет их как artifact `test-results`, а скриншоты —
прежним отдельным artifact. Сумма длительностей параллельных групп не равна времени CI.

## Небольшие данные для обычных тестов

Фикстура `database` всегда применяет настоящие миграции к новой схеме. По умолчанию
она использует выбранные реальные локации из Git-каталога вместо всех
1448. Родители добавляются автоматически; nearby и redirects сохраняются только
в пределах выбранного набора. Затем работает настоящий `seed`, на временном
каталоге, с тем же промптом. Исходный Git-каталог и production-код не изменяются.

Если проверяются полный каталог, полнота поиска, импорт/idempotency, реальные
географические связи или историческое преобразование всей географии, добавляй:

```python
@pytest.mark.full_catalog
def test_catalogue_import(database):
    ...
```

Для целого файла можно задать `pytestmark = pytest.mark.full_catalog`.
Маркер определяет **данные**, а не CI-профиль: эти проверки приложения остаются
и в `app`. Не ослабляй существующие ожидания ради маленькой фикстуры; выбери полный
каталог, если он требуется сценарию. Для нового обычного сценария предпочтительнее
создать нужные ему данные внутри теста.

Миграции и изменяемое состояние не разделяются между тестами. Клонирования шаблонной
БД и отката общей транзакции пока нет: это отдельная возможная оптимизация после
измерений, с учётом проверок многопоточности и фоновых процессов.

## Локальный запуск

Нужны Docker, Compose и отдельный тестовый PostgreSQL. Секреты production не нужны.

```sh
docker build --target test -t involta-guide:test .
export TEST_DATABASE_URL=postgresql://test:test@127.0.0.1:5432/guide_test
deploy/test-container.sh python deploy/run_tests.py --profile full
# Обычные проверки приложения:
deploy/test-container.sh python deploy/run_tests.py --profile app
# Последовательно, например для диагностики:
deploy/test-container.sh python deploy/run_tests.py --profile full --workers 1
```

Для одного теста остаётся прямой `deploy/test-container.sh pytest ...`.
На локальном Docker VFS оставляй запас места и запускай проверки реального
многоконтейнерного стека отдельно от pytest. На production тесты не запускаются.

## Проверенное дерево PR после merge

Main push может пропустить повторный verify только при доказанном совпадении
Git tree и подходящего профиля с успешным same-repository PR run. Сохраняются
конкретный run attempt, SHA сборки, image ID и артефакт. Иначе выполняется обычный
путь выше. workflow_dispatch всегда запускает проверки. Подробности и границы
доверия: [IMAGE_RELEASE.md](IMAGE_RELEASE.md#переиспользование-pr-после-merge).
Тесты селектора находятся в test_ci_reuse.py, настоящий save/load образа —
в tests/deployment/test_promote_image.py. Все существующие проверки сервера
после деплоя остаются обязательными.
