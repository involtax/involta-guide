## 1. Актуальные требования владельца

Прежняя редакция `docs/VOICE_SERVICE_SPEC.md` из `90c396f` устарела в части модерации и публикации. Актуальная модель:

- Голос посетителя прежде всего создаёт сохранённый текстовый отзыв. Предложения изменений — сопутствующий результат; пустой список или ошибка анализа не теряют текст/аудио.
- Единица модерации — один отзыв с целым пакетом результатов. Редактор смотрит «было / станет», может исправить пакет, затем одобряет или отклоняет его целиком. Независимого принятия предложений по одному нет.
- Одобренные изменения сразу применяются к текущей странице. Черновиков страницы и отдельной публикации нет. Версии и причинно-следственная история сохраняются.
- Привилегированный голос редактора/Алекса может сразу менять разрешённые ему данные, например вступление. Полномочия проверяет сервер, сохраняется источник и история. Не ломать действующий доверенный путь.
- Сейчас обычные отзывы проходят ручное одобрение. Архитектура должна позволить позднее вызвать тот же механизм из автоодобрения; включать автоодобрение сейчас не требуется.
- Логи остаются общей страницей с кнопками для авторизованного. Структурой админки и ЧПУ занимается отдельный Sol-админка; не проводить параллельную переработку его маршрутов и layout.

## 3. Одобрять целый пакет отзыва

Сейчас `approve` принимает только отзыв, а `approve-proposal` принимает отдельную правку. Это не соответствует актуальному сценарию.

Сделать один application-контракт принятия пакета: отзыв, выбранный processing run, revision пакета, ожидаемые версии затронутых данных, итоговые исправления редактора и idempotency key. Формы должны использовать этот контракт; публичные URL согласовать с Sol-админка.

В одной транзакции Guide проверить права, блокировки и expected revisions; провалидировать все конечные изменения; применить весь пакет; сохранить решение, before/after и новые версии. Невалидный элемент откатывает всё применение. Повтор того же подтверждения возвращает сохранённый результат, не дублирует ресторан/версию/решение. Изменившаяся страница, новый run или изменённый пакет после открытия экрана дают 409 с актуальным сравнением.

Перед одобрением пакет можно редактировать, в том числе убрать ошибочную правку, сохранив автора и before/after. Это редакция результата анализа, не черновик страницы. Принятие отзыва без изменений успешно сохраняет решение без пустой версии страницы. Отклонение сохраняет отзыв, аудио, предложения и логи; повторный анализ не отменяет уже применённое решение.

Сохранить связь: исходное аудио/текст → обработка и snapshot промпта → проверенный пакет → решение → фактический diff → версии. Учесть общие карточки ресторана в нескольких локациях: история должна позволять понять весь фактический эффект изменения, исторические снимки не должны подмешиваться к сегодняшним полям ресторана.

## 4. Использовать OPENAI_API_KEY

```text
Only OPENAI_API_KEY configured -> Voice key present: False
VOICE_OPENAI_API_KEY configured -> Voice key present: True
```

Исправить конфигурацию Voice, сообщения, env example, Compose/runbook и тесты: OpenAI-ключ берётся из `OPENAI_API_KEY`, остальные `VOICE_*` настройки сохраняются. Для отдельного контейнера значение передаётся через окружение/менеджер секретов, без ключей в исходниках. Не требовать от владельца второй копии секрета под новым именем. Когда переменная отсутствует, показывать понятную ошибку. Проверить, что значение не попадает в браузер, текстовые логи и документы.

## 5. Сделать сбой consumer наблюдаемым

В `src/involta_guide/infrastructure/voice/consumer.py:217` сейчас:

```python
try:
    worked = consumer.once()
except Exception:
    worked = 0
```

Исключение импорта скрывается, а цикл повторяется каждые три секунды. Недоступный сервис или событие, которое не удаётся импортировать, может остановить продвижение очереди без диагностического сообщения из этого обработчика.

Записывать безопасный structured log с причиной/типом ошибки, event ID/sequence, reference/run, когда они известны, и stack trace для внутренней ошибки. Сохранять наблюдаемое состояние последней попытки/ошибки/успешного продвижения; дать UI/healthcheck возможность отличить пустую очередь от застрявшей. Не логировать секреты или целиком payload с личными данными по умолчанию.

Временные ошибки повторять с ограниченным backoff. При невалидном событии нельзя молча продвигать cursor/ack и терять отзыв. Сделать диагностируемое состояние остановки на событии и безопасное возобновление после исправления. Проверить сбой до транзакции, rollback импорта, потерянный ack и повторную доставку.

## 6. Подготовить production-запуск, не запускать его

В PR добавлен `compose.voice.yaml` для локального запуска. Файлы существующего production deploy/Compose не подключают новый Voice API, Voice worker и `guide-voice-consumer`. Runbook предлагает запуск consumer отдельной командой. Поэтому обычный deploy Guide не разворачивает всю функцию; `VOICE_ENABLED=false` по умолчанию правильно сохраняет выключенное состояние.

Подготовить проверяемый production-путь в принятом механизме деплоя:

- Voice DB/роль, постоянный audio volume, API, worker и Guide consumer;
- приватная достижимость Voice из Guide/consumer, правильные credentials и переменные без значений в Git;
- отдельные миграции Guide и Voice в правильном порядке, readiness/worker/consumer checks;
- immutable image reference, без production build на сервере и плавающего `latest`;
- запуск consumer до включения новых загрузок, проверка передачи transcript/result;
- отказ Voice не ломает HTML-страницы Guide;
- rollback выключает новые поступления, но сохраняет доступ и обработку уже принятых записей; не откатываться на образ, не понимающий `voice:` audio references;
- только принадлежащие Guide/Voice сервисы, без изменений основного сайта, SSH, firewall, DNS и TLS.

Можно отдельным коммитом в том же PR или связанным PR, если так удобнее проверить, но интегрированная функция не считается готовой к включению до проверки этого пути. Production остаётся выключенным до команды владельца. Реальные секреты не запрашивать в чате и не создавать в документах.
