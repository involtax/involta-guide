# Локации, надлокации и редакционные подборки

## Модель

`locations` заменяет `cities`. Типы: город, населённый пункт, район, городская зона, курорт, туристическая территория, федеральная территория, направление. Любой тип может быть надлокацией. Основной редакционный родитель — `parent_id`; административный регион — отдельное поле. Идентификаторы прежних городов и URL сохраняются.

Связи «рядом и также интересно» хранятся отдельно от родителя. Они не означают территориальное включение. Циклы в основной иерархии блокируются и приложением, и PostgreSQL. Отключить родителя с включёнными детьми нельзя: сначала нужно перенести или отключить детей.

## Стартовая география

- Исходные 1134 города сохранены.
- Из 163 пользовательских добавлений получено 160 самостоятельных записей: Хаджох — дополнительное название Каменномостского; Газпром Поляна, Лаура и Альпика — одна локация.
- Добавлены связующие направления и отдельные сущности: Сочи-центр, горное направление Красная Поляна, одноимённый посёлок и курорт, Байкал, Ольхон, Малое Море и другие.
- Москва: 132 административных района во внутреннем справочнике и 20 согласованных гастрономических зон в публичной навигации. Четыре района используются повторно, без дублей. Троицк и Щербинка используют существующие ID и канонические URL.
- Полный список и источники: `data/SOURCE.md`. Справочник можно выгрузить в JSON из админки.

## Поиск и SEO

Короткий канонический URL не зависит от глубины дерева. Альтернативные названия участвуют в поиске без создания дублей страниц. Смена slug сохраняет постоянное перенаправление со старого URL; алиасы не могут захватывать адрес другой локации. Старые ссылки админки `tab=cities&city=...` также перенаправляются.

Заголовок собирается из «Где поесть» и редактируемой формы с предлогом: «в Сириусе», «на Розе Хутор», «на Патриарших». Есть цепочка родителей, canonical, BreadcrumbList и ItemList/Restaurant. Поле `listed` управляет каталогом и навигацией. Внутренняя административная территория появляется в публичном поиске после публикации полезной подборки. Надлокация с опубликованными дочерними страницами может индексироваться как полезная навигация, даже без собственного топа. Пустые страницы без наполненных потомков имеют noindex.

Поиск учитывает имя, дополнительные названия, регион, тип и редакционного родителя. Регистр и различия е/ё нормализуются. Каталог и админка используют пагинацию.

## Рестораны и публикация

У ресторана одна основная локация. `restaurant_locations` хранит дополнительные связи. Общая подборка направления ссылается на существующие ID: второй ресторан в БД не создаётся. Редактор может выбрать ресторан из опубликованной дочерней страницы либо явно связать существующий ресторан с другой локацией.

Для дочерней страницы и направления можно писать разные редакционные описания в снимках страниц. Правка общего снимка не меняет каноническую запись ресторана из дочерней локации. В список для выбора передаётся опубликованное описание дочерней страницы — её неопубликованные правки туда не попадают.

Сохранение общей подборки создаёт черновик. Публикация остаётся отдельным действием. На публичной странице ресторана из другого места указывается его основная локация. Дочерняя страница не подменяется ресторанами родителя.

## Наполнение и границы

Лимит топа задаётся редактором (1–10). Предположительная численность населения и условное население курортной территории на лимит не влияют. Допустимо получить меньше заведений или ноль.

Промпт получает конкретную локацию, тип, предлог/падеж заголовка, редакционных родителей, дочерние территории, описание охвата, существующие рестораны и лимит. Поддерживаются `{локация}`, `{регион}`, `{лимит}`, `{родитель}`, `{охват}` и прежний `{город}` как совместимый псевдоним. Рейтинг по восьми факторам сохраняется.

У локации можно задать проверенный центр и прямоугольник охвата. Эти данные не выдумываются при импорте. Прямоугольник — ориентир поиска, а не точный административный полигон; автоматического геокодирования и PostGIS-полигонов пока нет. У ресторана доступны необязательные координаты.

Массовое наполнение по умолчанию охватывает каталог: скрытые пустые административные районы не ставятся в очередь. Админ может отдельно выбрать такую территорию для наполнения.

## Обновление существующей установки

Перед переходом с версии только городов сохраните резервную копию PostgreSQL и аудио, остановите приложение и воркер. Для текущего Python-приложения выполните `uv run alembic upgrade head`, `uv run guide seed` и запустите web/worker заново. Alembic проверит legacy-ledger; уже выполненные SQL-миграции повторно не запускаются. Подробная процедура — в `docs/MIGRATION.md`. Миграция переименовывает таблицу и внешние ключи, сохраняя записи; старая версия кода с именем `cities` не рассчитана на новую схему.

Импорт выполняется по версиям и повторно не перезаписывает ручные изменения. Применённые SQL-миграции не редактируют. Для восстановления старой версии приложения нужен согласованный откат БД из резервной копии; удаления данных ради повторного импорта не требуется.
