# Бета: шесть распознаваний одного отзыва

Согласовано владельцем: для каждого **нового** отзыва сохраняются прежние GigaAM и
Parakeet через onnx-asr, плюс обе модели через Sherpa без словаря и со словарём.
Первичным публичным текстом остаётся прежний GigaAM. По итогам живого тестирования
владелец выберет один вариант; оценок/эталонов/модерации этот эксперимент не добавляет.

## Контракт и данные

Guide передаёт все названия из каталога выбранного города в
`SubmissionMetadata.location.recognition_dictionary`. Поле формирует сервер;
данные посетителя не задают список. Выборка не ограничена публичным топом или
200 строками и включает все записи данного города. Пробелы нормализуются,
точные дубликаты убираются, список сортируется. Иностранные названия сохраняются
как в каталоге; автоматические алиасы, склонения и LLM-правки не добавляются.

Список фиксируется в исходном контексте `runs.snapshot.location`. В том же commit,
что принимает аудио/receipt, создаются шесть stages с замороженными настройками.
Один исходный файл читается для каждого задания; повторная отправка с тем же
ключом не создаёт новые задания. При последующем изменении каталога ни словарь,
ни уже полученный текст не меняются.

Voice migration **8** расширяет ключ asr_candidates с `(submission,run,engine)`
до `(submission,run,engine,variant)`. Старые результаты получают variant=onnx,
остаются на месте и не дообрабатываются. Варианты: onnx, sherpa_plain,
sherpa_hotwords. Таблицы отзывов/истории/словарей не дублируются.
Точные словарь, параметры, ревизии, хеши входного аудио/PCM, время и raw-результат
сохраняются через прежние requests/provider_calls/asr_candidates. У каждого задания
свой lease, ошибка и ограниченное восстановление после остановки. Сохранённый raw
ответ повторно применяется без нового inference.

## Исполнение

Все шесть задач работают в прежнем voice-worker последовательно, исходный GigaAM
имеет приоритет перед сравнениями. При смене исполнителя прежняя тяжёлая модель
освобождается. Предобработка PyAV mono 16 kHz и Silero VAD с максимумом сегмента
20 s/минимумом тишины 500 ms одинаковы во всех вариантах.

Оба Sherpa-варианта используют modified_beam_search с четырьмя путями и одинаковыми
параметрами; отличается только наличие списка подсказок. GigaAM — E2E RNN-T с
пунктуацией, Parakeet — TDT 0.6B v3. Экспорты Sherpa отличаются от onnx-asr,
их repository/commit SHA закреплены в коде и записываются в каждый request.
Исходные экспорты/параметры onnx-asr не меняются. Модели работают на CPU.

Словарь передаётся Sherpa файлом строк UTF-8: это сохраняет `/` внутри названия,
который строковый per-stream API использует как разделитель. Файл существует
только во время загрузки графа; его содержимое остаётся в параметрах обработки.
BPE-представление подсказок получено из tokens.txt по официальному примеру Sherpa;
алгоритм отмечен `tokens-longest-match-v1`. Строка с управляющим префиксом `:`
вызывает наблюдаемую ошибку только данного сравнения, а не молча меняет веса.
Сила подсказок 1.5; length_reward=0.5 у Parakeet, 0 у GigaAM.

Только variant=onnx и engine=gigaam могут менять submissions.transcript и
посылать событие публикации в Guide. Остальные пять результатов, включая успешный
GigaAM/Sherpa, не служат fallback при ошибке primary. Удаление/epoch/reset fencing
и правила публикации 0/1 сохраняются.

## Проверка на настоящих моделях

Собрана CPU-библиотека из commit `3898de1380029e96a3b0a3df9e21e3f5ee5eb7fb`
с исправлением TDT #4084. Установка `uv sync --frozen --extra voice-local`
проверена в отдельном окружении с development headers Python 3.13; PEP 610
provenance подтверждает commit. Upstream `git_sha1` этой сборки сообщает старое
значение из version.cc, поэтому его нельзя использовать вместо provenance.

Для smoke использован публичный русский `test_wavs/example.wav` из pinned
репозитория экспорта GigaAM (11.29 s). Для длинного сценария пример повторён четыре
раза (45.16 s). **Это не записи владельца и не случай «Алхимист → оптимист».**
Все шесть вариантов вернули тексты на обоих аудио, с одинаковыми audio/PCM SHA256.
На длинном аудио модель сохранила четыре повтора; глобальный peak RSS процесса
с шестью последовательными обработками — 1370.5 MiB. Это память ASR-процесса на
проверочной машине, не всей production-системы и не обещание скорости VPS.

Время ниже включает загрузку модели; CPU threads=2:

| Вариант | 11.29 s, время s | 45.16 s, время s |
| --- | ---: | ---: |
| gigaam / onnx | 2.39 | 4.76 |
| parakeet / onnx | 5.10 | 6.58 |
| gigaam / sherpa_plain | 2.32 | 6.22 |
| gigaam / sherpa_hotwords | 3.65 | 12.23 |
| parakeet / sherpa_plain | 3.53 | 8.85 |
| parakeet / sherpa_hotwords | 3.37 | 8.09 |

Полные результаты, включая неудачные проверки на синтетической речи:
[native-results.json](design/voice-sherpa-comparison/native-results.json).
Локальный eSpeak-синтез «Алхимист/оптимист» оказался плохо пригоден для оценки:
часть вариантов, включая прежний GigaAM, не распознали речь. Он не используется
как доказательство исправления названия. Точность подсказок и силу смещения
проверять на живых отзывах; именно для этого сохраняются все шесть результатов.

## Сборка и выпуск

`uv sync --frozen --extra voice-local` собирает pinned Sherpa из исходников.
Для локальной сборки нужны development headers Python, C++ compiler и git;
CMake uv ставит изолированно. Production Docker строит библиотеку в builder-стадии,
готовому VPS компилятор не нужен. Версию из PyPI вместо pinned commit не подставлять:
релиз 2.0.1 ещё не включает исправление TDT #4084.

Перед первым запуском `voice prepare-model` загружает также Sherpa-экспорты
(~0.9 GB новых весов) и создаёт bpe.vocab/READY.json. Во время приёма/обработки
загрузки моделей нет. Production Compose явно выбирает полный профиль беты;
выключенного Sherpa-флага нет. Старые отзывы не запускаются заново.

Полный release: остановить writers → приватный Voice backup → voice migrate (8)
→ voice prepare-model → новые компоненты одного SHA. Guide Alembic остаётся
review_publication. Успешность/порядок и rollback: [VOICE_RUNTIME.md](VOICE_RUNTIME.md).
Миграцию и восстановление схемы 7 проверяет real pg_dump/pg_restore smoke в CI,
сохраняющий также проверки исходных схем 5/6. Сам production этой задачей не меняется.
