# Involta Guide: упрощение архитектуры для проверки основного сценария беты

Статус: самостоятельное ТЗ на реализацию для Sol. Контекст чата не требуется.
Актуализация: 2026-11-03. Проверенный `main`: `ad1d56b597b9283f41bb47315bb1a8ea94b79555`
(включены PR16 — единый виджет/диагностика и PR17 — дизайн админки).

## 1. Цель и решения владельца

Продукт сейчас — бета для тестирования основных функций. Приоритет: понятный код,
однозначные сущности, удобная диагностика, возможность полностью очистить эксперимент.
Не проектировать будущую большую платформу и не сохранять ненужную совместимость.

Основной сценарий:

```text
Первое наполнение локации
  → человек записывает голос
  → сохраняются аудио, исходный текст отзыва и метаданные
  → ИИ предлагает изменения
  → администратор рассматривает пакет «было → станет»
  → одобрение сразу меняет актуальные данные страницы
```

Обязательные решения:

1. У обычной локации одна собственная подборка. Ресторан принадлежит ровно одной
   локации. Общих ресторанов между локациями нет.
2. У надлокации нет собственной подборки. Сейчас она показывает подлокации;
   в будущем сможет выводить топ из их ресторанов. Будущий общий топ НЕ делать.
3. Наполнение создаёт исходные данные один раз. Дальше развитие — через отзывы
   и текущие разрешённые ручные действия, а не повторную генерацию подборки.
4. Исключение беты — административный полный сброс локации с новым наполнением.
   Сброс удаляет ВСЁ связанное содержимое, включая отзывы, аудио, обработки и логи.
   Не делать архивы, перепривязку отзывов, поиск соответствий или восстановление.
5. Хранить исходные IP, User-Agent и нашу cookie посетителя, а не заменять их хешами.
6. Подробные публичные логи наполнения пока оставить для дебага. Закрытие отложено.
7. Редакторский голос полностью убрать. Любая новая запись, в том числе от
   вошедшего администратора, — обычный отзыв с обычной модерацией.
8. Старые адреса и форматы удалённых механизмов не поддерживать.

Этот документ имеет приоритет над прежними ТЗ/описаниями репозитория в перечисленных
вопросах: общие рестораны, повторное наполнение, сохранение старых отзывов при сбросе,
редакторский голос, хеширование метаданных. Прямые более свежие указания пользователя
имеют приоритет над документом.

## 2. Границы работы и актуальное состояние

Оставить Python/FastAPI, серверный HTML/Jinja/HTMX, PostgreSQL и отдельный Voice.
Очереди в PostgreSQL остаются; новые брокеры, кэши, микросервисы и framework событий
не нужны. Не возвращать React, черновики страниц, снимки содержимого и публикацию
отдельной кнопкой.

В свежем main уже сделаны:

- ЧПУ административных разделов (`docs/ADMIN_ROUTES.md`).
- Прямое редактирование вступления, актуальные данные без версий страниц.
- Один встраиваемый frontend `src/involta_voice/static/widget.v1.js` для всех ролей;
  прежний отдельный frontend уже не подключается на странице локации.
- Бета-диагностика записи, локальное сохранение blob в IndexedDB и повтор отправки.
- Обновлённый дизайн админки (`docs/ADMIN_DESIGN.md`).
- Локальное сравнение GigaAM/Parakeet (`docs/ASR_BETA.md`). Это отдельный текущий
  эксперимент, не выбирать победителя и не удалять сравнение в этой задаче.

Frontend теперь общий, но backend всё ещё выбирает старый редакторский путь по
сессии. Убрать именно это раздвоение, сохранив сделанные UI-исправления.
ТЗ жестов Telegram/удержания/тишины ОТЛОЖЕНО; не реализовывать его здесь.

Работать от свежего `origin/main`, в своей ветке/checkout. Перед началом проверить
новые изменения и PR, не откатывать работу других агентов. Не запускать дополнительных
агентов без поручения пользователя. Результат — проверенный PR, без production-деплоя.

## 3. Целевая модель данных

Логические сущности ниже — требования к смыслу данных, а не приказ создать по новой
таблице на каждый пункт. Переиспользовать существующие подходящие таблицы.

| Сущность | Ответственность и связи |
| --- | --- |
| Локация | География, slug, родитель, признак надлокации, настройки видимости, вступление обычной страницы, текущая revision |
| Ресторан | Одна конкретная запись с одной `location_id`; карточка, телефон, часы, позиция/видимость и оценки в своей подборке |
| Аудиозапись в Voice | Оригинальный файл, метаданные, идентификатор отправки, локация и метка её текущего цикла |
| Обработка аудио | Попытка с зафиксированными моделями/промптами, стадиями, результатами и диагностикой |
| Отзыв в Guide | Полный оригинальный текст, редакторский текст при наличии, локация, авторские метаданные, состояние модерации |
| Упоминание/оценки | Фрагмент отзыва и связь с рестораном той же локации; один отзыв может упоминать несколько ресторанов |
| Предложение | Предлагаемое изменение, принадлежащее отзыву и конкретной обработке |
| Решение модератора | Кто и когда рассмотрел пакет, что одобрено/отклонено, какие диффы применены |
| Запуск наполнения | Единственное первоначальное наполнение текущего цикла локации: вход, модель, ответ, состояние применения |

### Локации и рестораны

- Сохранить дерево `locations.parent_id`, защиту от циклов и текущие типы географии.
  Не создавать отдельные сущности города, района, курорта и надлокации.
- Надлокация — явно `is_hub=true`. Рестораны могут принадлежать только обычной
  локации. Backend запрещает создание ресторана/наполнение в надлокации.
- У надлокации сейчас только навигационная страница. Убрать там кнопку наполнения
  и виджет отзыва на собственную подборку; дать переходы в подлокации.
- Наличие дочерних страниц, доступность, sitemap/canonical и индексация навигационных
  страниц должны работать; пустой собственный список надлокации не делает её ошибкой.
- `restaurants.location_id` — единственная принадлежность. Удалить
  `restaurant_locations`, attach/detach интерфейсы, связанные API/запросы.
- В записи хранить активность и оценки критериев. Порядок и итоговый балл
  вычислять, не хранить отдельно: полные восемь целых оценок 0–10 → среднее
  по убыванию, без полной оценки → после оценённых. При равенстве — стабильный
  номер ресторана по возрастанию. Номер в ЧПУ не является местом в топе.
  Сайт и админка используют одно правило. Отзывы и звезда не меняют порядок.
  Кнопка «Ещё» и `top_limit` продолжают работать. Подробно: RESTAURANT_RANKING.md.
- Оценки и пояснения для текущей подборки хранятся у ресторана; оценочная структура
  может быть JSONB. Связи с рестораном/локацией — обычные FK, не ID внутри JSON.
- Удалить `locations.page_data.restaurants` как второе хранилище состава/порядка.
  Если после переноса данных `page_data` не нужен — удалить поле целиком.
- Отчёт исследования, исключённые кандидаты и сырой ответ — данные запуска наполнения.
  Текущая страница читается из локации и ресторанов даже без диагностических логов.
- Не делать дедупликацию по картам/телефону/названию, объединение дублей и сохранение
  ID при повторной генерации. Это сознательно отложенная работа беты.
- Не создавать перенос общего ресторана между подборками и будущую агрегацию топов.
  Отдельную массовую миграцию географии не делать.

### Отзыв — обязательный самостоятельный результат

- Сохранять расшифровку до дополнительного анализа. Ошибка анализа не удаляет её.
- Исходный текст не заменять резюме ИИ. Редакторский текст хранится отдельно.
- Отказ модератора/фрод сохраняет отзыв и причины до явного бета-сброса локации.
- Нет предложений — всё равно есть отзыв. Одобрение только отзыва не должно
  искусственно менять ресторан/вступление.
- Предложение нового ресторана не создаёт ресторан в каталоге до одобрения.
- Пакет одобряется атомарно; существующая возможность корректировать/исключать
  предложения сохраняется. Автоодобрение и автоматический пересчёт топа не включать.
- Все restaurant references в пакете принадлежат локации отзыва. Чужую локацию
  сервер отвергает, даже если ИИ или клиент прислал такой ID.
- Разделять состояние обработки и решение модератора. Счётчик «ожидает модерации»
  считается по модерации, а не по техническому `status=pending` распознавания.
- Сохранять численные атрибуты: тональность -10..10, рекомендация -10..10,
  оценка 0..10; отсутствие оценки не превращать в ноль.

## 4. Наполнение: кто, откуда и сколько раз

| Операция | Доступ | Правило |
| --- | --- | --- |
| Первое наполнение | Любой посетитель, кнопка на публичной обычной локации | Один активный запуск, только до первого успеха текущего цикла |
| Повтор неудачного первого наполнения | Администратор из конкретного лога | Без лимита ручных повторов в бете, один активный запуск |
| Продолжить получение уже заказанного ответа | Существующий worker / ручное действие администратора | Тот же ответ провайдера, без нового платного POST |
| Повторная валидация сохранённого ответа | Администратор | Только пока первоначальные данные не применены успешно |
| Генерировать заново после успеха | Только администратор через полный бета-сброс | Прямая перезапись успешной подборки запрещена |
| Наполнение надлокации | Никто | Операции нет |

У локации достаточно `initialized_at` и ссылки на успешный запуск, если она нужна
для UI. Признак успеха НЕ вычислять по текущему числу ресторанов: после удаления
последнего ресторана публичная генерация не должна включаться снова.

Очередь/ошибки отображаются в существующих логах. Настройки промпта и модели
сохраняются в «Настройках наполнения», сохранение настроек не создаёт заданий.
Массового наполнения/отдельного набора очереди нет. До первой попытки публичная
кнопка запускает; при ошибке посетитель видит статус, повтор заказывает администратор.

Успех — одна транзакция: проверка актуального цикла/revision/lease, запись
начальных ресторанов и вступления, отметка `initialized_at`, состояние применения.
Повторный callback не добавляет вторую копию ресторанов.

После успеха запрещены и скрытые backend-пути regenerate/reprocess, способные
перезаписать подборку. Старый успешный лог даёт просмотр и переход к бета-сбросу.
Повторный анализ ОТЗЫВА остаётся отдельной разрешённой операцией администратора.

Ошибку/неизвестный исход платного POST не превращать в автоматическую новую покупку
ответа. Сохранить текущий механизм background GET/polling. Лимиты активных заданий
и технические лимиты числа вызовов действуют; денежного учёта нет; «без лимита повторов в бете» означает отсутствие
счётчика запрета ручного сброса, а не отключение всей защиты от двойной отправки.

## 5. Полный бета-сброс одной локации

Кнопка в административной карточке: **«Очистить локацию и наполнить заново»**.
Защищённый POST, например `/admin/locations/{slug}/reset-and-fill` под BASE_PATH.
Нужны действующая admin-сессия, CSRF и понятное подтверждение с названием локации
и указанием, что отзывы/аудио/логи будут удалены. Действие только для обычной локации.
Сохранить текущую обработку повторного клика: один сброс и один новый запуск.

### Что остаётся

Сама запись локации и её идентичность: ID, slug, название, география, родитель,
соседние/навигационные связи, видимость и прочие настройки справочника. Глобальные
настройки промптов/моделей, сессии администраторов, другие локации не затрагиваются.

### Что удаляется полностью

- Все рестораны локации, их оценки, позиции, звёзды и текущие данные подборки.
- Вступление обычной страницы, начальный отчёт/результат наполнения, `initialized_at`.
- Все отзывы этой локации: тексты, raw-метаданные, оценки/фрагменты, предложения,
  решения модераторов, ручные диффы и прежние редакторские записи, если остались.
- Аудиофайлы и производные файлы на серверах Guide/Voice, а также архивные копии
  приложения, привязанные к этим записям. Не создавать архив при удалении.
- Задания, lease/ожидания, обработки, результаты, запросы/ответы провайдеров,
  номера/привязки логов, подробные диагностические события этой локации.
- В Voice — submissions/runs/stages, ASR-кандидаты/оценки/события, provider calls,
  archive bindings, относящиеся к ним outbox-события; в Guide — соответствующие
  inbox/import records, links, debug upload reports, pending failures.
- Любые появившиеся к моменту реализации дополнительные зависимые таблицы/файлы:
  исполнитель составляет полный список по фактической схеме, не ограничивается
  названиями выше. Включить список в PR и тест сброса.

Никаких сохранённых отзывов с оторванным рестораном, перепривязки, tombstone
на каждый отзыв, снимков страницы или «корзины». Старые URL удалённых объектов
не должны открывать чужие новые данные.

### Защита от возвращения удалённого содержимого

Две БД и файлы не имеют общей SQL-транзакции. Не маскировать частичное удаление
надписью «Готово» и не строить универсальный распределённый transaction framework.

Рекомендуемый минимальный механизм:

1. В локации одна техническая монотонная метка `content_epoch` и признак
   незавершённого сброса. Это НЕ история страницы. При начале сброса под блокировкой
   повысить epoch и закрыть новые приёмы/применения для этой локации.
2. Все задания, отправки аудио, Voice-события и импорт проверяют свой epoch перед
   фиксацией результата. Старая попытка не может писать в новый цикл. Проверка
   должна быть атомарна с записью; одной предварительной проверки недостаточно.
3. Voice получает идемпотентную внутреннюю команду очистки локации с новой меткой.
   Он блокирует поздние старые submissions/worker callbacks, удаляет данные и файлы
   своего владельца. Минимальная запись текущего epoch/состояния локации в Voice
   допустима: без неё старый HTTP-запрос может прийти уже после удаления.
4. Удалить зависимости в Guide. Подтвердить фактическое удаление файлов и данных
   Voice; затем завершить сброс и поставить ровно один новый первоначальный запуск
   с новым epoch, зафиксированными промптом и моделью.
5. Если Voice недоступен или удаление файла не удалось, состояние — «Сброс не
   завершён» с причиной и возможностью продолжить. Новый запуск ещё не стартует.
   Повтор после падения процесса продолжает ту же очистку идемпотентно.

Допустимо одно небольшое рабочее состояние/список файлов незавершённого сброса;
после успеха его убрать. Это не архив удаляемых данных. Файлы нельзя потерять из
списка очистки, удалив их DB-ссылки до фиксации задания на удаление.

Не требуется физически убить уже отправленный OpenAI-запрос: попытаться отменить,
если API позволяет; его поздний результат никогда не возвращается в БД/логи/страницу.
Это относится и к коду диагностики: обработчик ошибки не должен заново записать
старый отзыв/лог после epoch-сброса. Учёт глобальных лимитов без содержимого
локации можно оставить агрегированным; чужие задания/данные удалять нельзя.

Глобальный outbox sequence, cursor другого потока и последовательности публичных
идентификаторов НЕ сбрасывать. Пропуски номеров нормальны. Номер нового лога не
переиспользует старый URL: хранить монотонный счётчик на сохраняемой локации, а не
`max(number)+1` по удалённым логам. Аналогично номерам отзывов и ресторанов.

### Поздняя отправка из браузера

Виджет уже сохраняет аудио в IndexedDB. Привязать сохраняемую отправку к epoch:
после сброса старый blob/key не должен автоматически отправиться как новый отзыв.
Backend отвергает старый контекст; виджет показывает, что локация сброшена, и
очищает её устаревшую локальную очередь при следующем контакте с сервером.
Не подставлять свежий epoch в старую автоматическую попытку. Сознательная новая
запись создаёт новое намерение/ключ. Не обещать, что сервер моментально удалит
файл из IndexedDB закрытого чужого браузера; гарантируется отсутствие его повторного
восстановления на сервере. Все серверные копии приложения должны быть удалены.

## 6. Один обычный голосовой поток; редакторского голоса нет

Voice — отдельный backend со своим аудиотомом, схемой `voice` в общей БД и ASR-worker ([runtime](VOICE_RUNTIME.md)), который:

1. Принимает запись через same-origin gateway Guide и надёжно сохраняет её.
2. Расшифровывает, хранит исходный текст и диагностические результаты ASR.
3. Запускает анализ с зафиксированным специальным промптом, выдаёт предложения.
4. Доставляет результаты Guide. Не меняет каталог и не принимает решения модератора.

Guide владеет каталогом, текстовыми отзывами, модерацией и применением пакета.
Обычная запись всегда становится обычным отзывом независимо от admin-сессии.

Удалить рабочие ветки:

- Переключение upload в редакторскую команду по `admin/alex` сессии.
- `data-actor=admin` как режим команды, специальный редакторский виджет/надписи.
- Интерпретатор `AlexCommands`, отдельный промпт, автоматическое применение
  редакторского голоса, старые jobs вида review для второго голосового pipeline.
- `guide_transcription` мост для старого Guide-исполнителя, ожидание ASR внутри
  `OpenAIProvider.transcribe`, лишние архивные адаптеры и маршруты, когда потребителей нет.
- Журнал/таблицы исключительно редакторских команд, связанные формы/кнопки,
  мёртвые DTO/тесты. Старые команды не превращать в пользовательские отзывы.

Административный вход и ручные действия не удалять. Не реализовывать заново
секретные URL или права звезды. Существующее поле звезды можно оставить как
атрибут ресторанов; из голосового предложения оно не меняется.

Сохранить текущие полезные исправления frontend: запись/прослушивание, поддержка
MIME, IndexedDB, retry того же blob/key, ошибка с понятным текстом, диагностика,
история собственных отзывов, очистка tracks/object URLs, независимое встраивание.
Не переписывать дизайн и не добавлять жесты из отложенного ТЗ.

## 7. Исходные метаданные посетителя

Сохранять в явных полях или типизированном объекте:

- исходный IP, определённый сервером с корректным доверием к настроенному proxy;
- исходную строку User-Agent;
- исходное значение нашей visitor-cookie `guide_visitor` (если отсутствует,
  сервер назначает её перед отправкой и сохраняет одно и то же значение);
- время получения, локацию, язык, часовой пояс и имеющиеся технические параметры
  аудио: MIME, размер, фактическую длительность.

Не заменять IP/UA/visitor ID HMAC/SHA и не вводить вторые поля только ради старого
формата. `visitor_identity()` и аналогичные преобразования удалить из нового пути.
Стабильный случайный visitor ID допустим — сохраняется именно значение cookie.
Owner-only история проверяет его на backend; нельзя доверять visitor/role/IP,
присланным произвольными полями формы. Администратор видит исходные метаданные.

Речь именно о cookie посетителя проекта, не о сборе всех cookies браузера.
Пароли, admin session tokens, CSRF и API-ключи в метаданные/публичные логи не писать.
Хеш аудиофайла сохранить для целостности и повторов; хеши паролей/сессионных секретов
тоже не затронуты требованием хранить исходные пользовательские метаданные.

Старые хешированные IP восстановить невозможно: не выдавать их за raw и не
строить ради них совместимость. Для одноразового перехода допустимо удалить
старые бета-записи в явно обозначенном шаге перехода.

## 8. Рабочее состояние отдельно от логов

Сейчас `generation_run` в `audit.detail` используется как источник модели,
baseline revision, публичности и параметров переобработки. Это убрать.

- Все параметры выполнения принадлежат заданию/запуску: model, prompt snapshot,
  location/epoch, baseline revision, provider response ID, состояние и факт применения.
  Допустимо расширить существующие `jobs`/`generation_requests`, не создавать
  отдельный generic workflow engine.
- Успех API, прохождение валидации и применение результата — различимые состояния.
  Экран не должен объявлять страницу наполненной только потому, что API вернул 200.
- Запрос/ответ, нужный для незавершённой обработки или ручной повторной проверки,
  остаётся частью результата запуска. Его удаление отличается от очистки trace.
- `audit`/trace только отображает события. Удаление диагностических событий не
  меняет модель, правила видимости, идемпотентность или проверки применения.
- Сохранять один понятный формат диффа по полям для наполнения, отзыва и ручного
  вступления. Отдельной сущности «версия страницы» нет; смотреть историю через источник.

Существующие `/logs/{slug}/{number}` и публичный дебаг наполнения оставить. Не
создавать `/admin/logs`, не закрывать сейчас публичные логи. Административные кнопки
по-прежнему требуют сессию/CSRF. Raw-метаданные и аудио чужих посетителей остаются
доступными администратору/владельцу по текущим правилам, не становятся публичными
из-за сохранения публичных логов наполнения. Сохранять маскирование секретов.

## 9. Очереди, ошибки и транзакции

### Ошибка одного события не останавливает остальных

Сейчас Consumer прерывает цикл на неимпортируемом событии и повторяет его раньше
остальных. Исправить через минимальный статус доставки/ошибки в существующей
inbox-механике: сохранить ошибку и вход события надёжно, дать повтор из админки,
продолжать независимые отзывы. Не добавлять новый broker или сервис.

Нельзя просто увеличить cursor и потерять ошибочное событие. Продвижение cursor/ack
разрешено только после надёжной фиксации результата либо ошибки для повтора.
Сохранять порядок зависимых событий одного отзыва и уникальность их применения.
Событие старого epoch после бета-сброса игнорируется как ожидаемо устаревшее,
не создаёт удалённые записи и не становится вечной ошибкой очереди.

### Worker не ждёт чужой worker

После удаления редакторского моста в Guide нет 15-минутного polling распознавания.
Voice обрабатывает свои стадии, consumer доставляет результаты. Наполнение
продолжает использовать отложенный background polling, освобождая Guide-worker.
Не заменять очередь ожиданием внутри HTTP-запроса.

### Только локальные блокировки

Удалить `SELECT ... FROM locations ORDER BY id FOR UPDATE` без ограничения локации
и обход всех страниц в поиске общих ресторанов. Для изменения блокировать текущую
локацию, её отзыв/пакет и нужные рестораны в стабильном порядке.

Сохранить три предохранителя: один логический запрос при повторном нажатии,
атомарное применение пакета, запрет устаревшего результата. No-op не создаёт
фиктивный дифф/revision. Не убирать lease и idempotency как «лишнюю сложность».

## 10. Переход и удаление старого кода

Данные беты не требуют архивирования. Не делать матрицу миграций всех исторических
релизов и двусторонние адаптеры старого/нового формата. Достаточно чистой установки
и проверенного прямого перехода с актуального main/схемы.

Исполнитель до изменения схемы перечисляет текущие FK/файлы и выбирает короткий
переход. Географический справочник, slug, глобальные настройки и административный
доступ сохраняются. Старые бета-отзывы/логи и несовместимое содержимое можно очистить
в явно описанном шаге. Не запускать массовую очистку на каждый старт приложения.
Обычные рестораны переносить с их единственным владельцем; вторичные привязки убрать.
Если у надлокации осталась старая собственная подборка, её содержимое очистить
как бета-данные, не клонировать в дочерние локации и не придумывать за пользователя
новую географию. Указать такие изменения в отчёте перехода.

Удалять старые реализации вместе с вызовами, DTO, маршрутами, шаблонами, настройками
и тестами именно удалённого поведения. Не оставлять вечные feature flags для
редакторского голоса или двух источников состава страницы. Сохранить явный временный
флаг бета-сброса (`BETA_RESET_ENABLED` либо эквивалент) и публичного первого наполнения;
отключённый флаг блокирует backend, не только кнопку.

Обновить Docker/Compose/проверки только в необходимой мере. Нельзя ломать проверки
release SHA, healthcheck, последовательные деплои и откат образа. Если переход
схемы несовместим со старым образом, явно описать поддерживаемый порядок отката;
не заявлять rollback, который запускает старый код на новой несовместимой БД.
Это не основание строить продуктовую историю данных. Production в этой задаче
не очищать и не деплоить: подготовить и проверить переход в тестовой БД.

## 11. Проверки приёмки

1. Обычная локация наполняется первым публичным запуском. Надлокация не принимает
   наполнение/рестораны/отзыв на собственную подборку, показывает подлокации.
2. Два одновременных клика создают один запуск. Ошибку повторяет администратор,
   посетитель не создаёт новую платную попытку. После успеха regenerate/reprocess
   не работают через прямой POST; удаление последнего ресторана не включает кнопку.
3. Вступление и рестораны читаются без page_data/диагностических logs. Обновление
   промпта/модели не меняет уже поставленное задание. Очистка trace не меняет работу.
4. Отзыв «Был в Огоньке сегодня, было вкусно» сохраняет полный текст и raw IP/UA/cookie.
   Ошибка анализа сохраняет аудио/текст. Отказ/фрод не удаляет их до сброса.
5. Администратор через тот же виджет создаёт обычный отзыв; «измени вступление…»
   не исполняется автоматически. Старые редакторские endpoints/DTO не обходят это.
6. Одобрение пакета применяет изменения сразу и атомарно; исключённое предложение
   не применяется. Повтор того же решения не дублирует действия. Чужой ресторан
   отвергается. Устаревшая revision даёт понятный конфликт, no-op не меняет страницу.
7. Два независимых города редактируются без глобальной блокировки всех локаций.
   При конфликте внутри одной локации нет потери изменений.
8. Ошибочное Voice-событие доступно для повтора; следующее независимое событие
   импортируется. Повтор/потеря ack не создают второй отзыв и не теряют сообщения.
9. Полный сброс проверяется на реальных PostgreSQL Guide+Voice и временных аудиофайлах:
   заполнить все зависимые таблицы, включая ASR/diagnostics, выполнить сброс и
   проверить отсутствие строк/файлов старого цикла. География/настройки/сессии целы.
10. Во время сброса другая локация продолжает работать, её данные и cursor не сброшены.
    Саму очищаемую локацию нельзя наполнить/модерировать/загрузить в обход блокировки.
11. Сброс одновременно с generation/ASR/анализом/import/upload: поздние ответы не
    возвращают удалённое содержимое, не создают старые логи и не применяются к новому циклу.
12. Прервать сброс после каждого внешнего шага, перезапустить обработчик: очистка
    продолжается без архива и второй генерации. Ошибка файла/Voice не выдаётся за успех.
13. Старый IndexedDB retry после сброса отвергается, не получает новый epoch молча.
    Пропажа ответа 202 в обычном цикле всё ещё повторяет тот же blob/key без дубля.
14. Новый цикл создаёт новые логи без повторного использования старых URL. Удалённые
    отзывы/логи не читаются по прежним ссылкам. Нет восстановления/перепривязки.
15. Публичные generation logs остаются доступны; административные действия защищены.
    Raw visitor metadata видит администратор, не посторонний посетитель. API-ключей нет.
16. Сохранены актуальный дизайн, embedding, диагностика, local audio recovery,
    списки/ЧПУ админки, «Ещё», телефон/часы и ручное вступление. Проверить desktop/mobile.
17. Чистая установка и прямой переход с текущей схемы проходят. Выполнить принятые
    lint/typecheck/tests и относящиеся к изменениям deployment checks. В тестах
    использовать fake provider; платные production-запросы не запускать.

Не писать тесты только на структуру нового кода. Нужны проверки наблюдаемого
поведения, гонок и фактической полноты удаления.

## 12. Порядок реализации и результат

1. Прочитать свежий main и связанные docs, составить компактную карту удаления
   legacy и целевых таблиц. Отразить в PR, не останавливаться на плане.
2. Убрать редакторский backend-путь, сохранив готовый единый frontend.
3. Упростить каталог/наполнение/рабочее состояние; сделать локальные блокировки.
4. Реализовать полный бета-сброс, epoch и устойчивую доставку Voice.
5. Проверить весь основной сценарий и сброс, обновить документацию, открыть PR.

В PR обязательны: краткая итоговая схема, перечень удалённых механизмов и таблиц,
план перехода, список удаляемых при сбросе зависимостей, результаты тестов и
сценарий ручной проверки со ссылками. Указать непроверенные устройства/ограничения.
Не мержить и не деплоить без отдельной команды.

Обновить `CURRENT_STATE.md`, `VOICE_API.md`/DTO/OpenAPI, `ADMIN_ROUTES.md`, `LOGS.md`,
`TEMPORARY_PUBLIC_FILL.md`, `LEGACY_REMOVAL.md` и необходимые runbook. Отметить
устаревшие требования в прежних spec, чтобы следующий агент не восстановил их.
`LEGACY_REMOVAL.md` должен содержать только фактически оставшиеся временные механизмы:
бета-сброс, публичный первый запуск, публичные debug logs и отдельный ASR-эксперимент.

Критерий завершения: весь сценарий беты работает через один понятный путь;
локацию можно полностью очистить и наполнить снова; удалённые данные не возвращаются;
в коде нет второй скрытой реализации того же процесса.
