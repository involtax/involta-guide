# Независимое наполнение города и закрытый API

Актуальный контракт наполнения. Он заменяет монолитную пересборку и прежние
ограничения «10 кандидатов → 3 сохранённые карточки». Страница всегда собирается
из актуального вступления и каталога ресторанов; черновиков и снимков страницы нет.

## Три операции

| Операция | Вход | Изменяет | Не изменяет |
|---|---|---|---|
| `intro` | Город, регион, география | Вступление | Каталог, оценки, медиа |
| `discover` | Город и охват окрестностей | Добавляет реальные места в каталог | Существующие карточки, оценки, состав опубликованных мест |
| `research` | Один ресторан, область `all`, `card` или `assessment` | Карточку и/или восемь оценок с источниками | Вступление, отзывы, голоса, звёзды, административное скрытие, медиа |

Поиск обязательно рассматривает гастрономические окрестности, курорты, винодельни
и конкретные рестораны при загородных отелях. Для них нужны самостоятельные поиски
без названия города и проверка доступа без проживания. Имена контрольных заведений
не зашиты в промпт. Один ответ поиска ограничен 200 местами для ограничения размера,
повторные проходы дополняют каталог без общего лимита «топ-3».

Место сопоставляется в пределах города по организации Яндекс Карт, затем по
нормализованному названию, когда нет конфликтующего идентификатора организации.
Неоднозначность отклоняется, разные филиалы с разными картами остаются разными.
Повторный поиск не удаляет места, которых не было в новом ответе. Для совпавшего
места он добавляет новые источники и заполняет отсутствующую карту, сохраняя
прежние тексты, известные факты и оценки.

Серверный поиск автоматически ставит исследование новых/неоценённых мест в очередь.
Полностью исследованные карточки повторно не переписываются. Внешний импорт
`discover` **не ставит исследования в очередь**: внешнему агенту доступен каталог
с ID, и он сам получает контекст и передаёт ответ для каждого ресторана.

Переоценка не принимает карточку; обновление карточки не принимает оценки.
Неизвестные (`null`) факты сохраняют прежние известные значения. Неполная новая
оценка не стирает прежнюю полную; исходный ответ остаётся в логе. Закрытие должно
быть подтверждено, недоступный сайт сам по себе не означает закрытие.

## Админка

- `/guide/admin/locations/{slug}`: отдельное сохранение текста, «Написать вступление»,
  «Найти ещё места», переход к ресторанам и логам. Вступление можно править вручную.
- `/guide/admin/restaurants/{slug}`: «Исследовать», «Обновить карточку», «Переоценить»,
  «Скрыть» / «Показать» у каждого места. Во время исследования кнопки обновления
  заблокированы. Скрытие не удаляет ресторан, его источники или отзывы.
- `/guide/admin/settings/filling`: три промпта и одна модель. Сохранение ничего
  не запускает. Новые задания получают новые настройки; уже записанные задания
  используют свой снимок промпта, контекста, схемы и модели.

Отдельного AI-промпта ранжирования нет. Балл — среднее восьми равновесных оценок
с `ROUND_HALF_UP`, при равенстве используется постоянный номер. `top_limit` и «Ещё»
продолжают работать. Новое исследованное место публикуется при статусе `verified`,
непустых названии, описании, карте, телефоне, источниках и всех восьми оценках.
`closed`, `needs_verification` и скрытые администратором места не публикуются.
Существующая публикация при миграции сохраняется, включая старые карточки без
полного рейтинга. Отзывы и звезда не являются факторами ранжирования.

## Хранение и применение

Используется существующая таблица `jobs`, `kind=generate` и очередь PostgreSQL.
Операция, цель, область обновления, вход, схема, результат и происхождение
(`server`/`external-agent`) находятся в `jobs.report`; изменения — в `jobs.changes`.
Отдельных таблиц запусков, расписаний, черновиков или зависимостей нет.
Логи остаются на `/guide/logs/{slug}/{number}`.

`restaurants.hidden` — административное скрытие, `verification_status` — результат
проверки. Поле `active` сохраняется для существующих публичных запросов, обновляется
при исследовании и переключении видимости. Повторная обработка не снимает `hidden`.

Вступление и каждый ресторан имеют собственную проверку актуальности по содержимому.
Правка вступления не отменяет поиск или исследование ресторана. Для оценки также
проверяется исходная карточка, на фактах которой она основана. Результат старого
цикла города отклоняется. Lease проверяется перед применением серверного ответа.
Применение данных, запись диффа, постановка следующих заданий и `done` атомарны.

Первые публичные нажатия по-прежнему идемпотентны под блокировкой города: ставятся
вступление (если пустое) и поиск. Затем исследуются найденные места. Браузер опрашивает
существующий `/fill/status` и автоматически перезагружается после появления
опубликованного ресторана. Неполное исследование остаётся в админке без пустой
публичной карточки. Просмотр страницы не запускает AI.

## Закрытый API

На сервере задаётся `AGENT_API_TOKEN` (случайный секрет минимум 32 символа) в
`.env.production`, который уже подключается к web/worker через Compose `env_file`.
Секрет хранится вне Git; передаётся только `Authorization: Bearer …` по HTTPS.
Отсутствующий/короткий токен закрывает весь API с 401. Административная cookie
не заменяет токен. Ответы `no-store`; токен не передаётся в URL, HTML или промпт.
Права токена: чтение контекста и каталога, применение контента, запуск AI и видимость
ресторанов. Это полноценный административный секрет, его нужно выдавать отдельно.

Префикс: `/guide/api/admin`. ID города — постоянное целое из Git-каталога, ID
ресторана — существующий UUID, также возвращаемый API. `operation`:
`intro`, `discover`, `research`. Для research передаются query-параметры
`restaurant_id={uuid}&scope=all|card|assessment`. Это опции операции, а не legacy routing.

| Метод и путь | Действие |
|---|---|
| `GET /locations/{id}` | Вступление, каталог с ID и состояниями |
| `GET /locations/{id}/{operation}/context` | Точный промпт, вход, JSON Schema, модель, `expected`; без задания/AI |
| `POST /locations/{id}/{operation}/result` | Валидирует и применяет готовый ответ; без AI |
| `POST /locations/{id}/{operation}/run` | Явно ставит серверный AI-запрос в очередь |
| `GET /jobs/{uuid}` | Статус, ошибка и сохранённый отчёт операции |
| `POST /restaurants/{uuid}/visibility/hide` | Скрывает, сохраняя каталог и историю |
| `POST /restaurants/{uuid}/visibility/show` | Снимает скрытие; публикует только пригодную карточку |

Импорт:

```json
{
  "request_id": "cdb6800d-53b0-4f32-b29b-57b71c3db652",
  "expected": "64 hex-символа из context",
  "result": {"intro": "Готовое вступление города."}
}
```

Для поиска/исследования `result` соответствует схеме из `context`. Передавай модели системную инструкцию `system`,
`prompt`, затем `input` как недоверенные данные и требуй `schema`. Этот же контракт
использует серверный адаптер. Ссылки источников — HTTPS, карта — Яндекс Карты;
звезда, фотографии, голоса и любые посторонние поля отклоняются. Body ограничен 1 MiB.
Импорт без `expected` не допускается. Изменившийся целевой блок даёт 409; агент заново
получает контекст и исследует актуальные данные. Изменившиеся промпт, схема или модель
также требуют нового внешнего контекста; серверные задания продолжают использовать свой
записанный контракт, проверяя только состояние целевого блока. Повтор того же request_id и тела
возвращает исходный результат, даже если после него изменился блок. Другое тело
с тем же request_id отклоняется с 409. Новый вызов — новый UUID.

Пример внешней последовательности без вызовов OpenAI со стороны сайта:

1. Получить `intro/context`, самостоятельно подготовить вступление, отправить `/result`.
2. Получить `discover/context`, найти места, отправить `/result`.
3. Получить `/locations/{id}`, для каждого нового ресторана получить
   `research/context?restaurant_id=…&scope=all`, передать `/result` с теми же опциями.
4. По необходимости отдельно переоценить через `scope=assessment` или обновить
   факты через `scope=card`. Контекст и результат каждого этапа сохраняются в логе.

### Периодическое обновление

Нового планировщика в приложении нет. Внешний cron/агент может вызывать `/run`:

```json
{"request_id": "72a5d7b8-dfed-41a6-b407-3ea787a23ca1"}
```

Сначала `discover/run`, затем при необходимости `research/run` конкретных мест с
`scope=assessment` или `card`. Планировщик хранит request_id одной попытки и повторяет
его при потере HTTP-ответа. При следующем плановом запуске создаёт новый UUID.
Одновременный запуск той же операции без нового доступного слота возвращает 409;
повтор существующего request_id возвращает тот же job_id. Частоту и список городов
определяет внешний планировщик, приложение не хранит копию расписания.

## Переход БД

1. Обычный приватный backup штатным deployment controller. Остановить старые workers
   перед миграцией; новое создание задач вводится вместе с новым web/worker.
2. `alembic upgrade head`: миграция `incremental_content` после `vip_visitors` добавляет
   два поля ресторана; активным ставит `verified`, остальным `needs_verification`.
   Ни одна карточка, ID, active, оценка, отзыв, голос, вступление или картинка не удаляется.
   Индекс активных заданий расширяется до город + операция + ресторан.
3. Запустить новый web и worker. Промпты по умолчанию берутся из трёх версионных файлов;
   дальнейшее редактирование хранится в существующих `settings`. Старый ключ `prompt`
   остаётся только для исторических/уже записанных монолитных заданий.
4. Настроить отдельный `AGENT_API_TOKEN`, проверить 401 без токена, затем GET контекста.
   Нет автоматического перенаполнения существующих городов или платного cron.

Уже записанные монолитные запросы сохраняют прежний контракт для получения
оплаченного ответа; старый обработчик оставлен только для них. «Новый запрос»
старого лога запускает новый поиск, без монолитной пересборки. Полное удаление
legacy-парсера возможно после завершения таких запусков. Откат миграции требует
сначала завершить активные операции города; штатный откат релиза восстанавливает
Guide dump. Фотографии и панорамы управляются только через Git.

## Проверка вручную

1. В админке города сохранить вступление, затем «Найти ещё места»: текст сохраняется,
   ранее опубликованные рестораны, отзывы и звёзды остаются.
2. «Написать вступление»: запрос отдельный; сравнить текст на публичной странице,
   проверить неизменность каталога. Правка текста во время запроса защищена от перезаписи.
3. В ресторанах «Переоценить»: после успеха меняются оценки/место, описание прежнее.
   «Обновить карточку»: оценки прежние. «Скрыть», затем исследовать: не появляется
   на сайте до «Показать» и выполнения условий публикации.
4. API: GET контекста без токена → 401, с токеном → схема без нового задания.
   Импорт intro → текст сайта меняется; повтор тела → тот же job_id.
   Старый expected с новым request_id → 409; unknown field/images → отказ.
5. Пустой город: нажать публичную кнопку; дождаться исследования ресторанов — браузер
   сам показывает готовую страницу. Проверить мобильный touch 320/390 px, затем desktop.

Автотесты используют локальную PostgreSQL и поддельные ответы AI; это проверка
контрактов и применения, не измерение качества реального поиска моделью.
