# Интерфейс взаимодействия Astra, sol1 и sol2

## Каналы и роли

Общий интерфейс — GitHub Issues и комментарии к PR в `involtax/involta-guide`.
Доступен из разных окружений через подключённую GitHub-интеграцию или `gh`.
Путь `/workspace/...` не означает общий диск. GitHub — общий источник задач
и зафиксированных решений; ветки/PR — общий источник кода.

| Участник | Зона ответственности | Канал |
| --- | --- | --- |
| Astra | Постановка задач, ответы, архитектурные решения, проверка пересечений, согласованный merge/deploy | Читает и пишет в оба канала |
| sol1 | Voice, отзывы, распознавание, анализ, модерация | [issue #12](https://github.com/involtax/involta-guide/issues/12) |
| sol2 | ЧПУ админки, настройки наполнения, ручное вступление | [issue #13](https://github.com/involtax/involta-guide/issues/13) |

На момент создания: sol1 работает в PR #10; задача sol2 описана в
[ADMIN_ROUTES_SPEC.md](ADMIN_ROUTES_SPEC.md). Если задача пользователя в отдельном
чате новее, она имеет приоритет: кратко отразить изменение в канале.

Это рабочие почтовые ящики, а не GitHub-аккаунты агентов. Все могут использовать
один аккаунт `involtax`, поэтому роль обязательно писать в тексте. Нельзя
подписывать сообщения за другого агента, считать ACK полученным без ответа
или считать issue живым подтверждением запуска чата.

## Формат сообщения

Первая строка: `[TYPE][from → to][task-id]`.

Типы: `TASK`, `ACK`, `QUESTION`, `ANSWER`, `STATUS`, `BLOCKED`, `REVIEW`, `DONE`.
Начальные task-id: `VOICE-001` и `ADMIN-001`. Для нового отдельного поручения
координатор назначает следующий номер; уточнения сохраняют исходный task-id.

Пример:

```text
[QUESTION][sol2 → sol1][ADMIN-001]
Reply-To: <ссылка на исходный комментарий, если это ответ>
Ветка: feat/admin-routes; HEAD: <полный SHA>; PR: #...
Нужна проверка: ручная правка intro обновит locations.revision.
Предлагаю отдельный сервис, сохраняющий текущий контракт применения Voice.
Затронутые файлы: ...
Зависимая работа: ...; независимую часть продолжаю.
```

TASK содержит конкретный результат, границы и критерии проверки. ACK сообщает
принятие, ветку, текущий SHA и план. DONE содержит PR/HEAD, фактические результаты
проверок и ограничения. BLOCKED включает точный безопасно отредактированный лог
ошибки: секреты и персональные данные не публиковать.

## Где оставлять сообщение

- Задача/вопрос участнику — в его issue. Ответ — в том же обсуждении с Reply-To.
- Вопрос sol2 к sol1 публикуется в #12; sol2 также проверяет #12, ожидая ответ.
- Изменение, затрагивающее обоих, — основной комментарий в одном канале,
  ссылка на него во втором; не поддерживать две расходящиеся копии решения.
- Замечания к конкретным строкам кода — в PR. В канале исполнителя оставить
  ссылку на review, чтобы он обнаружил его при проверке входящих.
- Задачи и существенные решения не хранить только в теле PR: оно редактируется
  и не служит очередью входящих сообщений. Уточнения публиковать комментариями.
- Прежде чем повторять поручение, прочитать уже существующие ответы/ACK.

## Рабочий цикл исполнителя

1. Получить свежие refs, прочитать этот протокол и оба issue, определить свою роль.
   Не делать reset/stash чужих незакоммиченных изменений.
2. Принять актуальную задачу ACK, указать ветку/checkout и план пересечений.
3. Работать самостоятельно. Проверять входящие перед началом этапа, перед
   изменением общих контрактов/схемы и перед push/PR/завершением. Во время
   длительной активной работы ориентир — раз в 60 секунд между операциями;
   не прерывать ради этого транзакцию или тест.
4. На вопрос отвечать в канале непосредственно; не отправлять пользователя
   переносить текст. Если ответа нет, продолжать независимую часть.
5. При блокирующей неопределённости описать точный вопрос и зависимую работу.
   Не менять спорный контракт на основании молчания. Не ждать бесконечным циклом.
6. В конце опубликовать DONE или BLOCKED. Перед завершением ещё раз проверить
   входящие, чтобы не потерять уточнения, пришедшие во время тестов.

Можно хранить последний прочитанный comment ID локально вне Git. После рестарта
перечитать обсуждение; не полагаться исключительно на непрочитанные уведомления.

## Рабочий цикл Astra

- При каждом входе в координацию прочитать оба issue, связанные PR и CI.
- Самостоятельно ставить конкретные задачи и отвечать на вопросы в GitHub.
  Пользователь не должен быть курьером сообщений между агентами.
- Проверять новые сообщения во время собственной активной работы тем же способом.
- Сверять контракты, миграции и общие файлы. Для правки возвращать исполнителю
  конкретное замечание с критерием проверки, не переписывать его ветку незаметно.
- Перед объединением проверить точные HEAD обеих работ и совместимость.
  Поручение настроить этот канал не является разрешением слить PR #10 или деплоить.

## Доступ через CLI

Читать тело задачи и комментарии (в том числе сообщения, написанные тем же аккаунтом):

```bash
gh issue view 12 --repo involtax/involta-guide --json body,comments,url
gh issue view 13 --repo involtax/involta-guide --json body,comments,url
```

Для длинной истории использовать пагинацию API, не ограничиваться последней
страницей; в API ID числовой, в `issue view` может быть GraphQL ID:

```bash
gh api --paginate repos/involtax/involta-guide/issues/12/comments
```

Публиковать сообщение, предварительно записав точный текст в локальный файл:

```bash
gh issue comment 12 --repo involtax/involta-guide --body-file /tmp/agent-message.md
```

В подключённой интеграции использовать эквивалентные операции чтения issues,
создания комментариев и review. Если доступ отклонён, показать точную ошибку;
не объявлять сообщение доставленным. Не раскрывать токены и env.

## Изоляция и пересечения

Своя ветка и свой checkout/worktree обязательны. Если диск общий, согласовать
разные директории; если инстансы разные, достаточно своих локальных checkout.
Не выполнять checkout/reset/clean в рабочей копии другого агента.

Наиболее вероятные пересечения: общая навигация и CSS, administrative routes,
location revision, editorial services, схема БД, конфигурация, CI/deploy. Перед
изменением общего интерфейса публиковать предложение; ожидание ответа требуется
только для зависимой части, не для всей работы. Sol2 не изменяет Voice routes,
DTO, таблицы отзывов и модерацию в рамках ADMIN-001.

Не коммитить heartbeat, stdout, приватные аудио или содержимое секретов ради
координации. Git хранит код и спецификации, issues — сообщения.

## Ограничение запуска отдельных чатов

Комментарий в GitHub не будит остановленный чат и не запускает модель. Протокол
работает, пока агенты исполняют свои задачи и проверяют входящие. Первое подключение
требует одной инструкции в каждом существующем чате. После завершения чата нужен
новый запуск пользователем; постоянного фонового диспетчера здесь нет.
Не устанавливать скрытый daemon и не запускать платные API-вызовы для имитации
пробуждения. Прямой автоматический обмен возможен для подагентов одного запуска,
но существующие независимые чаты нельзя присоединить к нему этим документом.
