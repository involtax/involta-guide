# Наполнение: один ответ исследования, живой голос гида

Инвольта гид — личный рейтинг Алекса. Вступление передаёт настроение города и
предвкушение еды; методология, источники и технический процесс остаются в логах.
Не выдумываем личные визиты или дегустации. Административная звезда принадлежит
только каталогу и администратору, не промпту или схеме модели.

## Контракт

| Граница | Содержимое |
| --- | --- |
| Ответ модели `GenerationResult` | `intro`, один список `candidates`, `discoveredRestaurants`, `warnings` |
| Кандидат | Название, статус/причина, факты карточки, `sources`, восемь `scores`, короткие `evidence` |
| Evidence | Фактор, короткое обоснование, уверенность, `sourceRefs`: номера sources этого кандидата с 1 |
| Сервер | Проверяет формат и связи данных, раскрывает ссылки, рассчитывает среднее и порядок, собирает карточки и отчёт полноты |
| Каталог/админка | Внутренние ID, принадлежность городу, звезда; эти поля не входят в ответ модели |

Первичное наполнение выбирает до 10 сильных кандидатов. Сервер рассчитывает
среднее восьми равных факторов и сохраняет только 3 лучших проверенных ресторана
(или меньше, если подтверждено меньше трёх). Все выбранные кандидаты, их оценки,
источники и причины решений остаются в отчёте job. Остальные обнаруженные названия
и известные источники сохраняются в том же каталоге с `active=0`, без дополнительного
исследования ради заполнения полей: [каталог](RESTAURANT_DISCOVERY.md).
Число 10 — максимум, а не требование выдумать недостающие места.

## Город и окрестности — одно гастрономическое направление

Поиск начинается с города и доступных окрестностей: загородных ресторанов,
курортных посёлков, ресторанов при отелях и винодельнях. Обычные места не вытесняют
сильный загородный ресторан только потому, что находятся в городской черте.
Это осмысленная поездка ради еды, с реальным подъездом, учётом сезонности и
возможности приехать внешнему гостю. Дегустации/разовые ужины сами по себе не
доказывают наличие работающего ресторана. Единого радиуса нет: прямое расстояние
через озеро не описывает доступность. Поиск не распространяется автоматически
на весь регион и далёкие самостоятельные направления.

`coverage_note` уточняет направление и ориентиры для исследования. При пустом поле
worker передаёт город, регион и доступные гастрономические окрестности, без «Только
[город]». Конкретный охват отдельно заданного района/курорта сохраняется.

Конкретные рестораны не закрепляются в охвате ради прохождения проверки.
Примеры владельца — ожидаемые результаты самостоятельного поиска:

| Вход проверки | Ожидаемая находка, не передаваемая модели |
| --- | --- |
| Анапа, регион Краснодарский край, общий охват окрестностей | «Винотеррия» |
| Медвежьегорск, регион Карелия, общий охват окрестностей | «Руна» при отеле «Заонежье» |

Названия, сайты и точные деревни этих ресторанов не входят в запрос. Сначала
модель самостоятельно находит места и проверяет факты, затем сервер сравнивает
кандидатов по прежним восьми равным факторам. Проверка различает обнаружение,
подтверждённые данные и попадание в итоговую тройку. Ни один этап нельзя объявлять
проверенным на основе искусственного ответа модели.

Ресторан сохраняется под ID города, вместе с городскими кандидатами. Отдельные
страницы микропосёлков, новые связи и поля не создаются. У загородного места
в `description` указан настоящий населённый пункт, а `mapsUrl` ведёт на точную карту.

`verificationIssues.location` означает неразрешённый адрес/филиал или принадлежность
направлению. `outside_area` — подтверждённый выход за гастрономический охват.
Адрес в соседнем муниципалитете при подтверждённой принадлежности направлению
не является ни тем, ни другим. Сервер не вводит геозону или дополнительную оценку
за удалённость; проверка доказательств/контактов остаётся прежней.

### Переход существующей БД

После обычного backup и остановки web/worker выполнить `alembic upgrade head`
(`city_surroundings` → `unbiased_city_scope`), затем обычный `guide seed` и запуск
сервисов. Историческая `city_surroundings` остаётся неизменной; следующая миграция
удаляет только две внесённые ею подсказки из `coverage_note`, если их текст ещё
точно совпадает с исходным. Ручной охват не заменяется. В новом Git-каталоге оба
поля пустые: worker использует общий охват города и доступных окрестностей.

Прежние значения записываются в аудит. Общий промпт, задания, сохранённый input,
вступления, рестораны, отзывы и сырые ответы не меняются; новых AI-вызовов нет.
У ещё не отправленного задания география собирается при первом вызове; уже
отправленный запрос продолжает использовать свой сохранённый input. Старые логи
могут содержать прежние подсказки: это история запроса, а не инструкция новому.
Повторный upgrade не затирает ручные изменения. Downgrade до `city_surroundings`
возвращает только удалённые значения и только пока поле остаётся пустым.

### Проверка качества промпта

Использовать реальный запрос приложения с общим промптом и пустым `coverage_note`.
Модель/параметры и полный input/output нужно сохранить. Ожидаемые названия остаются
за пределами запроса. Фиксировать отдельно: найден в candidates/discoveredRestaurants,
подтверждён для публикации, вошёл в тройку сервера. При пропуске улучшать общую
стратегию поиска, а не дописывать искомое название в охват города.

Первая попытка реального прогона: [входы и результат доступа](evaluations/unbiased-city-scope/README.md).
API отказал с `401 invalid_api_key`; самостоятельный поиск пока **не проверен**.

Автотесты на искусственном ответе проверяют сохранение и ранжирование загородного
ресторана, отсутствие названий/сайтов/деревень в отправляемом input и миграции.
Они не доказывают способность модели найти ресторан.

### Ручная проверка после выпуска

1. В `/guide/admin/locations/anapa` и `/guide/admin/locations/medvezhegorsk` проверить
   отсутствие автоматически закреплённых ресторанов в охвате.
2. При следующем отдельно разрешённом наполнении в `/guide/logs/anapa` или
   `/guide/logs/medvezhegorsk` проверить input: общий охват окрестностей, без
   ожидаемых названий, сайтов и точных деревень. До нового запуска старый лог
   остаётся прежним. Сам выпуск не запускает платный запрос и не сбрасывает город.
3. В реальном ответе проверить самостоятельную находку, источники, точное место,
   статус и место в тройке. Пропущенный ресторан — неуспех проверки качества поиска.
4. На `/guide/anapa` и `/guide/medvezhegorsk` проверить описание настоящего места,
   карту и порядок оценок. До нового разрешённого наполнения страницы прежние.

`verified` требует подтверждённые локацию/филиал, работу заведения, карту Яндекса,
телефон, кухню, описание и восемь численных оценок с источниками. Для каждого
фактора нужны ссылки `sourceRefs`. `verificationIssues` перечисляет конкретные
препятствия для `needs_verification`: location, operating_status, map, phone,
scores, evidence. Неизвестные часы/координаты и недоступный официальный сайт сами
по себе не блокируют публикацию. Подтверждённое отсутствие локальной связи —
низкий балл, недостаток сведений — null. Низкий балл не означает незавершённую проверку.

`excluded` требует outside_area/closed/not_restaurant/duplicate. Все статусы относятся
только к выбранной десятке. Полнота считается по ней; упоминания из предупреждений
не создают новых задач. Дополнительные обязательные условия не вводятся моделью.
Схема нового запроса `generation_v4` ограничивает candidates десятью элементами.

Текущий шаблон: [restaurant-research-v4.txt](../data/prompts/restaurant-research-v4.txt).
Он хранится в `settings.prompt` и редактируется в `/guide/admin/settings/filling`.
Runtime не дописывает второй контракт поверх редактируемого промпта.

Пример тона вступления (редакторский пример, не результат новой генерации):
«После прогулки по Иванову хочется тёплого света, вкусного ужина и долгого
разговора за столом. Здесь есть места, ради которых стоит задержаться».
Конкретику о блюдах и заведениях добавляем по фактической подборке.

## Выполнение и диагностика

`GENERATION_MAX_OUTPUT_TOKENS=32000` задаёт потолок ответа. Он включает рассуждения;
это технический лимит, не гарантированный размер результата. Сохранённый запрос
содержит фактически отправленный лимит. Изменение конфигурации не меняет уже
отправленный запрос. Один job делает один POST, последующие GET получают тот же
ответ. Проверка, fencing, baseline revision, атомарное применение и запрет
повторного наполнения готового города сохраняются.

Наверху лога показываются лимит, входные/выходные токены, доступные токены
рассуждений и понятный следующий шаг. `incomplete/max_output_tokens` — терминальный
результат: он сохраняется, не публикуется и не запускает автоматический повтор.
Для нового исследования используется явная кнопка нового запроса.
Переобработка того же ответа доступна только для сохранённого `completed`.

Регрессия Великого Новгорода:
[исходный лог](https://involta.ru/guide/logs/velikiy-novgorod/1),
[сокращённая фикстура исходного ответа](../tests/fixtures/novgorod-incomplete-response.json).
Сохранены исходный оборванный message, статус, лимит и usage. 8 карточек и оценки
10 кандидатов были записаны полностью, обрыв — внутри старого candidateReview.
Фикстура не является восстановленной/опубликованной подборкой.

## Денежного учёта нет

Guide и Voice не рассчитывают, не резервируют и не показывают стоимость.
Убраны денежные бюджеты, конфигурация тарифов и сравнение цен. `ai_usage` и
`provider_calls` остаются техническими журналами: состояние, токены, запрос/ответ.
Сохраняются дневные лимиты количества вызовов и ограничения очереди/параллелизма.

Исторические денежные поля в БД не удаляются: новые приложения их не используют,
а новые запросы не записывают стоимость. Старые дневные таблицы сохраняют счётчики
вызовов; неиспользуемое поле cost получает только нулевой технический placeholder
при создании нового дня, прежние значения не пересчитываются. Старые настройки
тарифов не читаются API/worker. Удаление истории не является частью этого перехода.

## Переход на тройку из десяти

Миграция `filling_top3` поверх `filling_v3` активирует новый промпт и обновляет
только ещё не отправленные задания. Отправленные запросы сохраняют свои input,
схему и ответы: v3 завершается по записанному контракту без нового POST. Это защита
уже отправленной работы; старые логи не восстанавливаются и не перегенерируются.
Downgrade восстанавливает прежний промпт и неотправленные задания, если они не
были изменены после upgrade. Повторный upgrade head не затирает ручные настройки.

Выпуск использует обычный backup/rollback Guide. Существующие каталоги и отзывы
не очищаются. Ограничение тройкой применяется при новом автоматическом наполнении;
ручные правки и отзывы продолжают использовать текущий каталог.

Проверки без платных API-вызовов:

```sh
PYTHONPATH=src uv run pytest -q tests/unit/test_research_contract.py \
  tests/integration/test_filling_top3.py tests/integration/test_filling_v3.py \
  tests/integration/test_city_surroundings.py \
  tests/integration/test_background_generation.py tests/integration/test_generation_quality.py
```

Проверяются выбор тройки и равные баллы, полный отчёт десятки, отсутствие часов,
реальные препятствия проверки, отказ на одиннадцатом кандидате, неизменность raw
response, отсутствие повторного POST и переход схемы. Для новых платных запросов
и production-deploy нужна команда владельца.
