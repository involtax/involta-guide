# Инвольта гид

[![Checks](https://github.com/involtax/involta-guide/actions/workflows/ci.yml/badge.svg)](https://github.com/involtax/involta-guide/actions/workflows/ci.yml)

**MVP · 0.1.0** · [Границы MVP](docs/MVP.md) · [Разработка](CONTRIBUTING.md) · [Безопасность](SECURITY.md) · [Изменения](CHANGELOG.md)

Справочник ресторанов по городам России: публичные HTML-страницы, редакционная админка, голосовые отзывы и очередь предложений ИИ. Next.js / React / TypeScript, SQLite (Node.js 24), локальное закрытое хранилище аудио.

## Запуск

```sh
npm ci
cp .env.example .env.local
# В .env.local задайте ADMIN_PASSWORD (от 12 символов)
# и SESSION_SECRET (случайная строка от 32 символов).
npm run dev
```

Сайт: `/guide`, админка: `/admin`. Для сервера с HTTPS установите `SITE_URL=https://involta.ru` и `COOKIE_SECURE=true`. Адрес SITE_URL должен совпадать с внешним origin, включая порт при локальной разработке: он используется в защите запросов, canonical и sitemap. Запись с микрофона работает по HTTPS или на localhost.

Города импортируются один раз при создании БД из `data/cities.json`. Источник и ограничения — `data/SOURCE.md`. 1134 записи; они доступны для ручного редактирования и отключения. Импорт не повторяется поверх существующей БД. Никакие рестораны для настоящего сайта не выдуманы и не предзаполнены.

## ИИ и очередь

Задайте `OPENAI_API_KEY` в окружении сервера. Не добавляйте ключ в Git. Модели по умолчанию: `gpt-4.1` с веб-поиском для наполнения, `gpt-4o-mini-transcribe` для аудио. Доступность выбранных моделей зависит от аккаунта API.

В отдельном процессе из корня проекта:

```sh
npm run worker
```

Оба процесса должны использовать одну БД и одно хранилище. Скрипт воркера читает `.env.local`. Сетевые вызовы сохраняют штатный proxy и TLS-проверку; Node.js запускается с поддержкой переменных прокси. Для облака нужен доступ к `api.openai.com`.

Вкладка «Наполнение»: сохраните промпт → выберите один город → поставьте задание → выполните воркером или кнопкой «Выполнить одно задание» → проверьте черновик → опубликуйте. Массовый запуск создаёт отдельные платные задания; в MVP результат каждого города проверяется и публикуется вручную. Ошибки видны в очереди и повторяются только вручную. Незавершённые задания старше 20 минут помечаются ошибкой при следующем проходе воркера.

## Модель публикации

- Город, база ресторанов, черновик и публичная версия разделены.
- Каждое сохранение создаёт версию **страницы**, с содержимым, источником, датой и промптом/моделью для генерации.
- Отдельного журнала промптов нет: редактор хранит текущую инструкцию, задания фиксируют её на момент запуска, версии страниц — реально использованную инструкцию.
- Черновики не влияют на сайт. Старую версию можно восстановить в новый черновик либо опубликовать напрямую.
- Публичные страницы отдаются готовым HTML с содержимым для SEO (серверный рендеринг, не набор статических `.html` файлов). Есть canonical, sitemap, Restaurant/ItemList JSON-LD. Пустые города имеют noindex и не входят в sitemap.

## Отзывы и модерация

Только микрофон, до 2 минут и 10 МБ. Сохраняются аудио, cookie-ID браузера, SHA-256 записи, HMAC IP, user-agent, расшифровка, результаты ИИ и решения редактора. IP считается по заголовку `X-Forwarded-For`; внешний reverse proxy должен заменять его, а не доверять входящему значению посетителя. Cookie и user-agent — признаки браузера, не надёжный отпечаток устройства.

Каждый осмысленный отзыв после обработки создаёт одну или несколько записей типа «отзыв с текстом» либо «оценка без текста», по упомянутым ресторанам. Дополнительные правки и новые рестораны предлагаются только при необходимости. Тональность и рекомендация: −10…10; оценка: 0…10. Неизвестное — null. Уверенность извлечения не означает достоверность рассказа.

Сохраняются **все** отзывы, независимо от одобрения или отметки фрода. Одобренные без фрода входят во внутренние средние; редактор вручную переставляет рестораны. Применение предложения создаёт черновик, не публикацию. Неизвестные ссылки и детали новых ресторанов админ должен заполнить перед применением.

Экран модерации содержит аудио, расшифровку, атрибуты, исходные цитаты, «было → станет», похожие записи. Сигналы: одинаковое аудио, тот же cookie/IP, лексическое сходство текстов. Анализируются последние 2000 записей; это базовый антифрод MVP, без семантических embeddings, CAPTCHA и автоматических блокировок. Несогласие с большинством не считается доказательством фрода. Посетитель видит статус по cookie только в своём браузере.

## Проверки

```sh
npm run check
npm test
npm run build
npm run test:e2e
```

E2E запускает production-сервер с изолированной временной БД и Chromium (системный `/usr/bin/chromium` или браузер Playwright; можно переопределить `CHROMIUM_PATH`). Проверяет вход, защиту API, черновик/публикацию, наличие контента в HTML, запись с тестового микрофона, cookie-историю и модерацию. Тестовые рестораны не попадают в рабочую БД. Скриншоты — `var/screenshots/`.

Тесты ИИ используют подставные ответы. Живые API-вызовы требуют ключа и оплачиваются отдельно.

## Развёртывание и ограничения MVP

```sh
npm run build
npm start
# второй процесс:
npm run worker
```

Один сервер с постоянным диском. `var/guide.sqlite` и `var/audio/` нужно сохранять и резервировать вместе; путь меняется через `DATA_DIR`. SQLite не предназначена для нескольких реплик приложения на разных дисках. При росте нагрузки следующий шаг — PostgreSQL и S3-совместимое хранилище.

Reverse proxy должен направлять `/guide`, `/admin`, `/api`, `/_next`, `/sitemap.xml`, `/robots.txt` в приложение. На существующем involta.ru маршруты `/admin`, `/api`, `/_next` могут конфликтовать: схема подключения к основному сайту ещё не проверена, до размещения нужно согласовать маршрутизацию или перенести служебные URL под отдельный префикс/поддомен.

У админки один пароль, сессия на 8 часов и ограничение попыток входа. Для публичного запуска нужны собственные настройки HTTPS, резервное копирование, согласованные условия обработки аудио и сроки его хранения. Автоматического удаления записей в MVP нет. Автоматическое ежедневное перестроение топов и автоматическая публикация не включены.

## Безопасность OpenAI API

Все обращения к OpenAI выполняются только backend-модулем `lib/ai.mjs`: серверным обработчиком админки или отдельным воркером. Единственный источник ключа — `process.env.OPENAI_API_KEY`. Ключ не передаётся в React-компоненты, HTML, JSON-ответы, localStorage, публичные переменные `NEXT_PUBLIC_*` или настройки сборки. При отсутствии ключа задание получает понятную ошибку, доступную только редактору. Тело ответа OpenAI и заголовки авторизации не записываются в ошибки.

В production передавайте ключ при запуске приложения **и воркера** через переменную окружения, которую предоставляет платформа деплоя или менеджер секретов сервера. Не включайте реальный ключ в Dockerfile, compose-файл, образ, конфигурацию Git или исходники. Для сборки ключ не требуется. `.env.example` содержит только пустое `OPENAI_API_KEY=`; локальные `.env`-файлы, каталог `secrets/` и файлы ключей исключены из Git.

## GitHub Actions

Workflow `Checks` проверяет типы, тесты, production-сборку и браузерный сценарий при push в `main` и в Pull Request. Production-секреты в CI не передаются; реальный OpenAI API не вызывается. Скриншоты тестовых страниц сохраняются как временный артефакт workflow. CI проверяет проект, но не развёртывает сайт.
